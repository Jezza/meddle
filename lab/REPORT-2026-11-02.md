# meddle under real network faults (tpo lab): report, 2026-11-02

Code under test: `main` at 32dc6775 (meddle 0.1.0, Claude Code version reported 2.1.314). Hermetic
setup as in README.md. Node-id order matters (the smaller id dials): run 2 had a<c<b, run 1 a<b<c.
Move phases were read from each node's `durable.sqlite` (`state.checkpoint.phase`) and task states
from `meddle.sqlite`, both read-only. All 13 scenarios ran end to end twice, plus extras 7c, 7d, 8b,
10b, 11b, 11c. **No task was ever live on two nodes.**

## Results (run 2 unless stated)

| # | Scenario | Result |
| --- | --- | --- |
| 1 | Up | PASS |
| 2 | Join through discovery | PASS |
| 3 | Token | PASS |

1. **Up.** Every serve up within 1 s; `status` in 372–420 ms; lighthouse `/v1/health` ok.
2. **Join through discovery.** Joins 514 ms (b) and 532 ms (c); all three pools showed everyone online
   1.3 s after c joined. The ticket carried the lab address, so `MEDDLE_IROH_BIND=$TPO_ADDR:0` works.
   How c learned a's address is not visible in any log (serves silent; the lighthouse logs nothing per
   request even at `RUST_LOG=trace`); scenarios 11b and 11c prove discovery works.
3. **Token.** Present on c 0.4 s after `token set` on a, mode 600.
4. **Project and task.** One turn 538 ms; the task bookmark in a's repo. Anomaly: `project add`
   silently runs `jj git init` on a plain folder.
5. **Degraded-link move** (a⇄b 80 ms, 2% loss). `task move` returned in 410 ms; b `idle` and a
   `moved` after 5.8 s; a turn on b 1.27 s; b's bookmark already in a's repo when the prompt returned.
6. **Partition before a move.** After `tpo cut b c`, `task move` on b exited 0 in 407 ms (`moving …`;
   c still online on b at that moment); c went offline on b 32.2 s after the cut, at the same moment as
   `meddle: move: … failed at handoff: aborted: call aborted` (39 s in the hand run); task live on b
   again. After the heal, c online on b in 1.3 s (13 s in the hand run).
7. **Partition during a move.** At 1500 ms delay with no cut a move takes 25.7 s: `handoff` 0–19.5 s
   (target `receiving` from +11.6 s), `commit` 19.5–24 s. Each cut `tpo cut b c --for 30s`.
   - cut at 4 s in handoff: run 2 the connection survived and the move completed; run 1 failed with
     `link to node closed: closed`, b stayed idle.
   - cut at 12 s in handoff: run 2 failed, c idle, b absent; run 1 and the hand run: b rolled back but
     **c kept a `receiving` copy**, created just as the cut healed, until c restarted.
   - cut ~2 s into commit: sender logged `waits for … to activate it: … did not answer within 30 s`
     then `aborted: call aborted`; the target activated after the heal and the move completed.
   - cut 3.3 s into commit with prompts to both nodes mid-cut: both refused (`task is moving; send it
     again once it has arrived` / `task is being received`); the move completed in about 71 s.
   In every run the node without the task refused prompts and a turn ran on the owner. Whether a 30 s
   cut kills the move depends on how it lines up with the ~30 s idle timeout.
8. **Crash mid-receive.** Stop after 4 s (no copy yet): the sender failed 1.5 s after the stop (a
   process kill is noticed fast, unlike a cut). Stop as soon as the target shows `receiving`: the
   sender failed with `no receipt` 11.7 s later; on restart the target dropped the partial copy within
   0.5 s, with no log line.
9. **Lighthouse outage** (60 s). All pools 3/3 online throughout; a move settled in 1.0 s; a and c
   each logged `discovery: announcing on http://lh:8080: request timed out after 10000 ms` once; b
   logged nothing (failed lookups are not logged); nothing shows announcing resumed.
10. **Node isolation.** A 20 s cut of c was never shown offline; a 60 s cut showed offline after
    32.0 s (a) and 31.1 s (b), online 1.3 s and 3.1 s after the heal.
11. **Restart.** a (smallest id) back online in 0.9 s with a new port (a dials everyone). The largest-id
    node took 26.3 s (after `pool: dialing …: timed out` on the others). With the lighthouse cut for
    45 s it came back only 19.4 s after the lighthouse healed (57.1 s after start): the lighthouse is
    the only path to a restarted high-id node's new address.
12. **Memory.** Each node's `MEMORY.md` held lines from a, b and c (10, 9, 11); the home's `memory`
    bookmark held all 11 turns; a node's working file lags until its own next turn (as documented).
13. **Resources.** RSS a 153 MB, b 148 MB, c 156 MB.

## Every anomaly

1. A stale `receiving` copy survives a rollback until the target restarts (orphans are swept only at
   serve start; the sender's `abandonTask` was lost in the cut). Prompts there fail with `task is being
   received`, the replica and task folder leak, and a later move of that task to that node from any
   other node would be refused with `already exists here`.
2. Dead peers take ~31–32 s to detect (the QUIC idle timeout); a 20 s outage is invisible; `checkMove`
   accepts a dead target.
3. No fast fail: the CLI reports success, the rollback comes 32–39 s later, and the message never
   says "unreachable".
4. `handoff`'s `receiveTask` has no deadline (`move.ts:102`).
5. A move under a 30 s cut takes about 70 s even when it succeeds (30 s activate timeout, then backoff).
6. Whether a move survives a 30 s cut is nondeterministic; both outcomes were safe.
7. A restarted high-id node rejoins in 17–26 s, and cannot rejoin while the lighthouse is down.
8. Log lines have no timestamps.
9. Successful moves and phase changes are not logged; phases appear only in failure lines.
10. Orphan sweeps and the release of a `moving` task left with no move are silent.
11. Discovery and lighthouse successes are silent; the lighthouse logs nothing per request.
12. Failed lookups are not logged, only failed announces.
13. Raw error text reaches the CLI, e.g. `unavailable: activating meddle.task{…}: unknown task`.
14. iroh logs `WARN noq_proto … failed closing path err=LastOpenPath` on every disconnect, plus
    `aborted by peer: the server refused to accept a new connection` while a peer restarts.
15. `MEMORY.md` lags on every node, the home included (as documented).
16. `project add` runs `jj git init` on a plain folder.
17. `status` counts a `moving` task as live on the sender.

## What to fix, most serious first

1. Sweep stale `receiving` copies periodically, not only at start (ask the sender, or time out copies
   with no import), and retry `abandonTask` after a rollback once the link is back.
2. Detect dead peers in seconds (application keepalives or a shorter idle timeout), and probe the
   target with a short-deadline call in `prepare` so a move fails fast with "unreachable".
3. Put a deadline on `handoff`'s `receiveTask`, or make it progress-based.
4. Redial as soon as discovery reports a new address, and let a freshly started node dial whatever the
   id order.
5. Timestamp log lines; log move phases and completion, orphan sweeps, discovery recovery and failed
   lookups; translate chord errors into plain messages.
6. Add `task move --wait` so the CLI can report the final outcome.
